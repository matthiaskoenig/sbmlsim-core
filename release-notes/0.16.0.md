# Release notes for sbmlsim-core 0.16.0

A measurement at the time of a change can read the state after the change. The output of a condition has two rows of that time, the state before the change and the state after it, and a curve read the first of them whatever the measurement meant: a fit of the measurements of PEtab, which are the state after a change, had to be run outside the engine.

## New

- **`after_change` of a curve of a request of `fit/1`** ([#58](https://github.com/matthiaskoenig/sbmlsim-core/pull/58), for [sbmlsim#607](https://github.com/matthiaskoenig/sbmlsim/issues/607)). One flag per measurement, in the order of the times:

    ```python
    request["curves"] = [
        {
            "condition": "dose",
            "column": "y",
            "times": [0.0, 5.0, 10.0],
            "values": [1.0, 0.74, 0.55],
            # the measurement at t = 5, the time of a change, is the state after it
            "after_change": [False, True, False],
        }
    ]
    ```

    A measurement whose flag is true reads the last row of its time, the state after the change and after every event the change fired; one whose flag is false, and every measurement of a curve without the field, reads the first row of its time, the state before the change, which is the behaviour of the releases before this one. A measurement at a time which is no change is unaffected, since such a time has one row.

    The flags are per measurement and not per curve, because the two meanings live in one curve: in PEtab a measurement at a change is the state after it, while the first point of a curve of sbmlsim is the state after the change and the later ones are the state before it.

    A curve whose field has more or fewer flags than the curve has times is refused, naming both counts (`Curve ... has 1 times and 2 flags of the state after a change`).

    The jacobian follows: it is read off the row a measurement resolved to, so a point which reads the state after a change has the derivative of that row and not of the one before it. A condition with a change carries no forward sensitivities, so such a fit takes the finite differences, which is what the tests cover (`crates/fit/tests/decay.rs`, five tests on a condition whose change at `t = 5` moves `y`: the state before, the state after, a flag which is false, a count of flags which does not match, and the jacobian of either side).

## Compatibility

A request of a release before this one has no `after_change` and fits exactly as it did. The field is optional and its absence is the old meaning, so nothing of an existing host changes.

A host which sends `after_change` to an engine of 0.15.0 or older is the one case to watch: that engine does not know the field and ignores it rather than refusing it, so every measurement would read the state before its change and the residuals would be wrong without an error. A host which uses the field requires 0.16.0, and sbmlsim floors it.
