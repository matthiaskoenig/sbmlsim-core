# sbmlsim-core 0.20.0

A change of `simulation/1` can carry a form, a value the engine computes from its own state at the change, so a caller which sets an entity by a formula over the entities of the model no longer folds that formula into a number.

## The form of a change, `forms` (#67)

A caller which sets an entity at a change by a formula over the entities of the model had to fold the formula into a number before it sent the request. That number is the one of the point the request was built at: a fit moves its parameters and the folded number does not, which changes the objective without a word.

`Change.forms` is a `Vec<Form>`, a `Form` is `{ target, constant, terms }` and `terms` is a `Vec<(String, f64)>` of an id and its factor:

```json
{ "times": [4.0], "forms": [{ "target": "dose", "constant": 25.0, "terms": [["weight", 0.5]] }] }
```

The value assigned to `target` is `constant + sum(factor_i * value(target_i))`. It is a linear form, the one a formula such as `25 + 0.5 * weight` is, and the engine evaluates it at the change from its own state:

- The terms are summed in the order of the request.
- Every term is read against the state **before** the change, so the order in which the values, the increments and the forms of a change are applied cannot change the value of a form.
- A repeated id adds its contributions, and empty `terms` is a pure constant.
- The target must be settable. A term need only be readable.
- An id is set, incremented or formed at most once per change.

A form is the increment it generalizes: an increment is the form of its own id with the factor 1.

The field has `#[serde(default, skip_serializing_if = "Vec::is_empty")]` as `increments` has, so a request without the key deserializes as before and a change without forms serializes unchanged.
