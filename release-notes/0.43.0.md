# sbmlsim-core 0.43.0

The statistics of `sbmlsim-stats` run in JavaScript as well: `sbmlsim-core/stats` exposes every function of `sbmlsim_core.stats` over `compiler.wasm`, with the same bits and the same errors (#170). The JavaScript host frees the buffers of `compiler.wasm` on every path and checks its allocations (#171). The documents of the ODEs of a model with an unsupported construct render again (#172), and continuous integration type checks the python tests (#169).

## The statistics in JavaScript (#170)

```js
import { createStats, StatsError } from "sbmlsim-core/stats";
const stats = createStats({ compiler: await createCompiler({ compiler: compilerWasm }) });
const u = stats.unitPoints(2, 1024, { design: "sobol", seed: 1 });
const [q, low, high] = stats.quantileCi(values, 0.95);
```

- **Every function.** The 46 functions of `sbmlsim_core.stats` in camelCase (`fisherStatistics`,
  `quantileCi`, `unitPoints`, ...) and its constants as members (`stats.EPS`, `stats.MARGIN`,
  `stats.MIXTURE`, ...). The required arguments of the python are positional, every optional or
  keyword-only one goes into a trailing object of options in camelCase; `undefined` or `null`
  takes the default of the python.
- **Values.** Arrays go in as plain or typed arrays, their nesting gives the shape numpy would
  see, and a seed may be a BigInt. A vector comes back as a `Float64Array`, a matrix as an array
  of `Float64Array` rows, a tuple as an array, a dict as an object with camelCase keys.
- **Errors.** An argument the python refuses throws `StatsError` with the `kind` of the python
  (`ValueError`, `OverflowError`, `ZeroDivisionError`, `IndexError`) and its message; a value of
  a wrong JavaScript type throws a `TypeError`.
- **One export.** `compiler.wasm` carries the statistics behind one export, `stats_call` (the
  feature `stats` of `sbmlsim-wasm`, on by default), over the raw C interface of its other
  exports. It adds 441 kB to `compiler.wasm` (124 kB gzipped). The inline build carries it as
  `sbmlsimCore.createStats`.
- **Same messages.** The checks of the arguments which python and JavaScript share live in
  `sbmlsim_stats::binding`, so both refuse a value with the same message. A size past a `usize`
  of 32 bits raises numpy's `ValueError` in WebAssembly as natively.
- **Tests.** 1020 calls of the python run through `compiler.wasm` with the same bits as natively
  and the same kinds and messages of their errors (`js/test/stats.test.mjs`).

See [JavaScript](https://matthiaskoenig.github.io/sbmlsim-core/javascript/#the-statistics) and
[Statistics](https://matthiaskoenig.github.io/sbmlsim-core/stats/).

## The buffers of `compiler.wasm` (#171)

- **Every path.** `compile`, `compileKernel`, `exportOde`, the PEtab calls and the statistics
  allocate their buffers through one helper (`withBuffers` of `js/compile.mjs`), which frees
  every buffer of a call, the results included, on success, on a refusal and on a throw.
- **Failed allocations.** An allocation `compiler.wasm` cannot make (a null pointer) throws
  instead of writing the document at address 0.
- **Byte order.** The words of a result are read little-endian at any alignment; pointers past
  2 GiB are read unsigned.
- **The wasm side.** `give` and the words of a refusal are written with `write_unaligned`, since
  the buffers of `allocate` are only byte-aligned.

## The documents of the ODEs (#172)

- **Unsupported constructs.** The markdown, LaTeX and Typst documents of a model with a construct
  its ODEs cannot express (a distrib function, the rate of an assigned size) failed in 0.42.0
  with `undefined value: u.id is undefined`; they list the construct by its label again.
- **Unit factors.** The magnitude of a unit factor is printed to 15 significant digits, so
  `6e-05 s` prints as `60 μs` instead of `60.00000000000001 μs`; a multiplier keeps every digit
  (`133.32239 N`).

## Development (#169)

- The python tests are type checked by ty in continuous integration (the job `python-bindings`),
  next to `python/typecheck`; seven type errors in them are fixed.

## Behaviour changes

- None of the python API. The JavaScript host frees and checks its buffers where it leaked or
  wrote to address 0 before (#171).
