# Release notes for sbmlsim-core 0.8.0

The reader reads the PBPK models of pkdb_models, which declare the distrib package as required to carry the uncertainty of every fitted parameter and which the reader refused until now, and a process no longer compiles `engine.wasm` before it can simulate: Wasmtime's persistent cache keeps the machine code of the engine, of its math library and of every model between processes, so a runtime costs 7.49 ms instead of 754.7 ms. The results of a simulation are the ones of 0.7.0, bit for bit.

## New

- **The reader reads a model which declares a package that only annotates (distrib)** ([#17](https://github.com/matthiaskoenig/sbmlsim-core/issues/17)). Every document which declared an SBML package with `required="true"` was refused, which kept every PBPK model of pkdb_models on roadrunner: those models carry the uncertainty of each fitted parameter as `<distrib:uncertainty>` (the hctz model alone has 55 of them, 1317 over all models). A package whose namespace URI the reader knows is now read, distrib so far and matched by its URI and never by its prefix, and of it only the five elements which annotate (`listOfUncertainties`, `uncertainty`, `listOfUncertParameters`, `uncertParameter`, `uncertSpan`). They compute nothing, so ignoring them changes no result. Every other element of that namespace is refused by name, `<distrib:drawFromDistribution>` above all: a draw changes the mathematics, and an engine which dropped it would simulate a different model than the document describes. The refusal is on the elements and not on the `required` flag, so a draw is refused in a document which declares distrib unrequired as well, which is a deliberate difference from the roadrunner engine of sbmlsim. Every other required package is refused as before (`comp`, which is flattened first, `fbc`, `multi`, `layout` and an unknown one), and a construct of distrib which a later version adds is refused rather than ignored.

- **Compiled modules are cached across processes**. `Runtime()` enables Wasmtime's persistent compilation cache for `engine.wasm`, `mathlib.wasm` and every model given to `load`, so the machine code Cranelift produced in one process is reused by the next. Measured on hctz in five alternating fresh processes, the median creation of a runtime falls from 754.7 ms to 7.49 ms and the loading of a model from 12.88 ms to 0.545 ms, with the same output bits. Python takes `Runtime(cache_dir=...)` and `Runtime(cache=False)` and reports the resolved directory as `runtime.cache_dir`; the constructor releases the GIL while it initializes the cache and compiles. The default is Wasmtime's platform cache directory (`$XDG_CACHE_HOME/wasmtime` or `~/.cache/wasmtime` on linux). Wasmtime keys an entry by the bytes of the module, the version of its compiler, the features of the CPU and the settings of the compilation, so a changed module or an incompatible configuration is compiled again; a missing, unreadable or corrupt entry and an unavailable directory are misses which fall back to compilation. The cache holds executable machine code and no simulation result, so it belongs in a directory only trusted users can write. The memory limit of an instance, the validation of a module and the execution deadline are unchanged, and the wheels stay portable. The SBML to WebAssembly compiler (`compile_sbml`) runs as before.

- **mimalloc is the allocator of the extension module**. The allocator is on the hot path of the compiler of a model and of Cranelift, not of a simulation, which allocates inside the linear memory of the engine: `compile_sbml` of a model of 919 states takes 21.0 % less time (124.6 to 98.4 ms), of a PBPK model 17.2 % less, `load` of the large model 7.5 % less and an uncached `Runtime()` 4.7 % less, and the peak resident set size of such a process falls by 23.0 % (430.2 to 331.4 MiB). A simulation and a batch are unchanged. It is set in the extension crate, which is a cdylib only, so it takes the choice away from no Rust caller, and it travels inside the wheel: unlike an instruction set it depends on nothing about the machine which installs it and cannot change a result. The wheels keep their tags and their floor (`manylinux_2_28`, no symbol above `GLIBC_2.28`) and grow by 54 kB.

## Measured and not taken

- **One wheel with several implementations of the engine and a dispatch on the features of the CPU** ([#15](https://github.com/matthiaskoenig/sbmlsim-core/issues/15)). Cranelift compiles `engine.wasm` on the machine which runs it and enables AVX2 and FMA from its CPUID already, and taking those features away costs nothing (0.97x to 1.04x), since the fixed-width SIMD of WebAssembly is 128 bits wide and relaxed SIMD is off by contract. In a native engine AVX2 (`x86-64-v3`) is worth 1.20x to 1.38x on the dense linear solver of a large model, which KLU beats by 10x to 48x in any case, and 1.02x to 1.10x everywhere else, and the compilation and instantiation of a model do not depend on the instruction set at all. The startup was what dominated a short run, which the cache above now removes. `bench/RESULTS.md` has the tables ("CPU features, the instruction set and the allocator").
