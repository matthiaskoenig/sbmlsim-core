# Release notes for sbmlsim-core 0.12.0

A parameter fit of a model runs in the engine, on the pool of the batch and with the forward sensitivities of CVODES as the jacobian of a step, and a panel answers the band of the uncertainty of its model next to its curves. The macOS wheel links no allocator of its own any more.

## New

- **A fit of a model in the engine** ([#45](https://github.com/matthiaskoenig/sbmlsim-core/pull/45), for [sbmlsim#556](https://github.com/matthiaskoenig/sbmlsim/issues/556)). The contract is `fit/1`, on the command line (`sbmlsim-core fit model.xml fit.json`), in python (`LoadedModel.fit`, `LoadedModel.fit_problem`) and in Rust (`sbmlsim_fit::Problem`). One evaluation of the objective is one simulation per condition in a single fan out over the threads, the residuals are interpolated to the times of the data, weighted and reduced in the worker, and a parameter is searched on the scale its bounds ask for (`lin`, `log`, `log10`). The optimizers are the bounded ones of [basin](https://crates.io/crates/basin) - `trust_region_reflective`, `levenberg_marquardt`, `differential_evolution` - with the tolerances, the iteration and the wall time limits and several starts per request. The identifiability of the optimum is the profile of the likelihood of a parameter with the interval where the cost rises by `chi2(0.95, 1) / 2`, and the Fisher information `JᵀJ` with the covariance, the standard errors and the correlations, which names the parameters the data does not determine when it cannot be inverted.

    **The forward sensitivities** are part of it: CVODES in place of CVODE, which is the same integrator and the same bits for a simulation without them, `sensitivities` of a request naming the parameters and `dy/dp` per row and column in the result. A step of a sensitivity moves what the initialization derives from it (`Vli = BW * f_li` of a PBPK model is an initial assignment, so the right hand side reads `Vli` and never `BW`), and `model_jac_p` of the compiler is the analytic `df/dp` of a model whose math has it, which is worth 1.86x of a jacobian of the sensitivities. A request whose sensitivities would be wrong is refused and says why; `engine.wasm` refuses them, its output format carrying no sensitivity table.

    `"jacobian"` of a request is `"auto"`, `"sensitivities"` or `"difference_quotient"`, and **`"auto"` takes the differences**: a run of `k` parameters costs about `1.2 (k + 1)` plain simulations whatever `k` is, the staggered corrector solving one linear system per parameter and step, so the sensitivities are the choice of a caller who wants the accuracy (1e-8 of itself against 1e-3) rather than the speed. `docs/fitting.md` is the page of the feature and `bench/OPTIMIZATION.md` holds the tables.

- **What a fit holds next to each other runs next to each other** ([#46](https://github.com/matthiaskoenig/sbmlsim-core/pull/46), [#47](https://github.com/matthiaskoenig/sbmlsim-core/pull/47)). A fit does not fill the machine by itself: between the fan outs the optimizer, the residuals and the linear algebra of a step run on the thread of the fit, and a fit of two conditions keeps about five of twenty threads busy. The starts of a multi start fit, the two sides of a profile and the profiles of the parameters now run on the pool of the batch together, each fanning its own evaluations out over the threads the others leave (`Workers::install` nests, and the instance of a point belongs to the thread which runs it): four starts of such a fit are 40.2 ms instead of 120.7 ms, the profiles of three of its parameters 160.6 ms instead of 341.1 ms, and nothing is slower where the conditions already fill the pool. The answer is the same one on one thread and on twenty, bitwise, and a stopped fit answers what ran. `scripts/fit_shapes.py` measures those shapes with the threads each keeps busy next to its wall time.

- **The band of the uncertainty of a panel** ([#50](https://github.com/matthiaskoenig/sbmlsim-core/pull/50)). A panel whose recipe carries an uncertainty - the sample of the fit of its model, which the bundle holds - answers a band next to its curves for the `draws` a request asks for. Every point of the grid is run once per draw, with the parameters of that draw set before the initialization, exactly as a knob with a `parameter` is, and the answer carries `uncertainty`: the `draws` it ran, the `fit` and the `level` of the recipe, the `band` of every curve (one `{low, high}` per point of the grid) and, for a run of a single point, the curves of the draws themselves. The sample is written in the order of its Latin hypercube, so the first draws of it are a stratified sample of their own and a band settles rather than jumps as a page asks for more.

## Fixed

- **Two extension modules which link mimalloc own the same two slots of the pthread TLS block on macOS** ([#48](https://github.com/matthiaskoenig/sbmlsim-core/pull/48), closes [#40](https://github.com/matthiaskoenig/sbmlsim-core/issues/40)). mimalloc does not keep the heap of a thread in a thread local there - a first access to a `__thread` variable can call `malloc` and recurse - and claims two slots by compiled in number instead, which are process wide. Two modules in one interpreter then allocate out of each other's heaps without a lock: the test suite of sbmlsim, which imports this module and `pkpdutils_core`, failed on macOS and only on macOS with 25 failures and 26 errors whose shape is heap corruption in code which has no bug. The dependency itself is gated now (`[target.'cfg(not(target_os = "macos"))'.dependencies]`), so the macOS wheel contains no mimalloc and compiles none of its C sources, and every other platform keeps it. `sbmlsim_core.__allocator__` reports which of the two a build is and `python/tests/test_allocator.py` asserts both halves of the gate against the built wheels.

- **A pool test which assumed which thread took a point.** `the_threads_reuse_their_instances_across_batches` asserted that the instances of a pool of two threads do not change between its first and its second batch, which holds only when the first batch reached both threads; which thread takes a point is rayon's to decide. It runs four batches now and asserts the promise the pool actually makes - an instance per thread, none dropped and made again - which a pool making one per batch still fails.

- **The parallelism tests measured the machine.** The two tests of #46 compared the seconds of the runs of a fit with a factor of the seconds of the whole, which is a claim about the runner: the two sides of a profile are of unequal length, and `develop` went red on the merge although the pull request was green. `next_to_each_other` of the fixture asserts what holds on any machine instead - a run of the chains next to each other saves at least half of what the shorter ones add to the longest - and passes under `taskset -c 0,1` and under `taskset -c 0`, while each of the three parallel paths made sequential still fails it.
