# Release notes for sbmlsim-core 0.9.0

The python package simulates on the native engine instead of `engine.wasm` in wasmtime, which is 1.9 to 2.3 times the speed of the wheel of 0.8.0 on the five models of the benchmark of sbmlsim. The model is the same `model.wasm` as before, so only the integrator changes, and what that costs is the last bits: a result of a wheel is no longer bitwise a result of the same model in a browser, and no longer guaranteed bitwise across platforms.

## New

- **The python bindings simulate on the native engine** ([#24](https://github.com/matthiaskoenig/sbmlsim-core/pull/24)). A wheel ran `engine.wasm` in wasmtime, which is the slowest of the hosts this engine runs on: measured on the five models of the benchmark of [sbmlsim](https://github.com/matthiaskoenig/sbmlsim) at its own configuration (`bench/sbmlsim.toml`, one performance core), one simulation took 0.020 to 69 ms there against 0.0097 to 37 ms natively, and V8 is 25 to 75 % faster than Cranelift on the same `engine.wasm`, so a browser integrated faster than python did. `crates/python` now takes `sbmlsim-host` with its feature `native`, so the integrator is compiled for the machine of the wheel (CVODE and SuiteSparse KLU from the submodules of `third_party`) while `model.wasm` and `mathlib.wasm` stay in wasmtime. Driven from sbmlsim, which also stopped making an instance per simulation, one simulation of the HCTZ model went from 2.34 ms to 0.876 ms.

    **A result is no longer bitwise the one of `engine.wasm`.** CVODE calls the `pow` and `sqrt` of the C library of the platform where it chooses its step size (`SUNRpowerR`), `engine.wasm` calls those of wasi-libc, so a result of a wheel is not bitwise a result of the same model in a browser or under `node`, and is not guaranteed bitwise across platforms either, the C library being the platform's. Within one platform and one wheel nothing changes: the C sources are compiled `-O3 -DNDEBUG -ffp-contract=off -fno-fast-math`, so no fused multiply-add and no fast math enter a result, every instance of a model integrates the same way, and a batch gives the results of a serial run bitwise whatever its threads. How large the differences are, measured: on those models the integrator took the identical path in the native engine, in wasmtime and under Node, all eighteen configurations of a model, a solver and a Jacobian agreeing on every counter (the 919 state model among them), so nothing of those results moved, and the largest relative difference from roadrunner at tight tolerances is the one of `engine.wasm` at every digit printed (4.32e-12, 0, 1.70e-08 and 1.20e-11). On the golden model, which has events, root functions and a steady state in its request, 3 of 30 values differ and the largest relative difference is 1.0e-14, against an integration at a relative tolerance of 1e-6. So the two engines can differ, and where they do it is near the last bits of a double and far below the error of the integration. `sbmlsim-core bench --host wasmtime` and the [JavaScript host](https://matthiaskoenig.github.io/sbmlsim-core/javascript/) remain the way to a result of `engine.wasm`, and `docs/python.md` has the section "The engine of the wheel".

- **`Engine::with_max_output_values`** bounds a result below `MAX_OUTPUT_VALUES`, and a native instance is given the memory limit of its runtime as that bound. The memory of a guest bounded the result of an instance of `engine.wasm`; the native engine allocates its result in the memory of the host, so without this `Runtime(max_memory_bytes=...)` would no longer bound a result at all. The check is the up-front one of the output times, so it raises the request error before anything is allocated.

- **`LoadedModel::instantiate_native` and `NativeInstance::simulate_prepared`** carry the whole API of the bindings on the native engine: an instance is made from the `model.wasm` the model compiled once, and a prepared request is resolved into a plan of the engine once per instance and kept, as an instance of `engine.wasm` keeps the plan of its guest. `NativeInstance` is `Send`, so a batch moves one into each worker of its rayon pool and keeps it for the points after the first.

- **The feature `native` no longer enables `sbmlsim-engine/test-models`**, so no test model travels in a wheel; the tests of `sbmlsim-host` reach `Decay` and `Robertson` through a dev-dependency instead.

## Changed

- **A source build of the python package compiles the C of the native engine** and not only that of mimalloc, so on a target of MSVC it needs the `clang` of LLVM on the path; `cl` cannot compile SUNDIALS. The wheels keep their tags and their floor (`manylinux_2_28`, no symbol above `GLIBC_2.28`). `docs/installation.md` says so.

- **The message of an output above the limit** names the limit and the memory of the engine in one sentence, since the bound is no longer the one constant.

- **A tag makes the release of this repository too** ([#22](https://github.com/matthiaskoenig/sbmlsim-core/pull/22)). The job `github_release` of `publish.yml` creates it from `release-notes/x.y.z.md` once PyPI and npm both carry the version, so a release of this repository never announces a version a registry does not have and nothing of a release is made by hand.

## Benchmarks

- **The documentation has a page of benchmarks** ([Benchmarks](https://matthiaskoenig.github.io/sbmlsim-core/benchmarks/)): the times and the ratios against roadrunner of every host, as tables and as a figure, written by `scripts/bench_figure.py` from the JSON of a run and generated by nothing at build time. The models are `bench/sbmlsim.toml` ([#23](https://github.com/matthiaskoenig/sbmlsim-core/pull/23)), the benchmark of sbmlsim at its own configuration, a second list next to `bench/models.toml`, whose tolerances and output grids differ, so each is comparable with itself and not with the other. The large model of that benchmark is measured with the rest now, the liver of a normothermic machine perfusion (919 states, 2.6 MB), with KLU alone, which is the solver a simulator picks for it.

    The host decides the comparison with roadrunner: natively the engine is faster on every model, by 1.4 to 12 times, and under V8 by 1.2 to 5 times, but in wasmtime it is slower than roadrunner on every model but `demo`, by 1.01 to 1.37. The wheel and the browser therefore both run the engine faster than the host this repository builds with.
